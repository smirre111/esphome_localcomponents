# Review — node, hub and protocol, 2026-09-15

Adversarial review of what changed since the last reviews: node since `22852ea`
(92 commits, ~9 000 lines of `main/`), `blinds.proto` (+495 lines: PhaseReport,
GridSync, GridBeacon, GridDemote, ModeTest/Report, header `onMark`/`fireStamped`,
GridSyncRequest), hub since `49d3216` (115 commits, ~2 250 lines in `lora_client`,
`lora_tracker`, YAML). Baseline for this review: node `f4c93c9` (fw 1.0.93), hub
`dcc52b4`.

Every finding below was checked against the code at that baseline; line numbers
refer to it. Nothing here is fixed yet.

### 1. Plaintext uplinks are acted on while the session is confirmed — High

**Where.** `lora_client.cpp:1758–1801`: on a confirmed session a plaintext frame is
held only to a msgid high-water mark (`:1788`), then goes to `dispatch_payload_`
(`:1799`) and to every cover component. `dispatch_payload_` (`:1514`) routes a
`CommandAck` to `notePhaseReport_` (`:3840`) and `handle_command_ack_` (`:2413`).

**What an attacker in radio range can do, with no key.** The msgid is plaintext in
every header, so beating the high-water mark is trivial.

* A forged `CommandAck` naming a msgid in the tracked command's range cancels its
  retransmissions and clears "command failed" (`:2445–2455`). A real command can be
  lost while Home Assistant shows success.
* The same ack for a `ScheduleConfig` push marks the schedule as landed and clears
  "Schedule Pending" (`:2430–2442`).
* The same ack for a GridSync stops the re-publish (`:2416–2426`).
* The ack's `PhaseReport` is stored unconditionally (`:3850–3857`). A forged
  `timedRxActive = true` can move the hub to single-shot for a node that is not in
  Mode B. Rule 4 bounds this to one frame per command, but it contradicts the plan's
  statement that the report is authenticated by a GCM tag.
* A forged `GridSyncRequest` costs one GridSync burst a minute (bounded by
  `hubAnswersSyncRequest`) — added today, same hole.
* `CoverPosition` and battery frames are forwarded to the cover components.

**Fix direction.** Mirror the node's default-deny: once `session_confirmed_`, drop
every plaintext uplink except REGISTER and LOGIN before `dispatch_payload_`. Tests:
a forged plaintext ack neither cancels a tracked op nor changes the phase belief; the
same frames still work while no session exists.

### 2. Header timing fields are not authenticated — High

**Where.** The AAD is `destAddress ‖ destSubnet ‖ senderAddress ‖ msgid` only
(`FrameCrypto.h:23–24`, `buildAad :74–82`). The hub writes `burstIndex`, `onMark`,
`fireStamped`, `fireRound` and `fireOffsetUs` into each copy's outer header at
transmit time and re-packs it around the same ciphertext
(`lora_tracker.cpp:1151–1184`).

**What the node does with them.** Phase samples, the settled re-solve of a
provisional anchor, the burst back-out, and since fw 1.0.93 the trial re-centre all
read these fields. The phase block (`CmdDispatcher.cpp:4858`) runs *before* the msgid
replay check (`:5041`), so a replayed genuine encrypted copy passes the GCM tag check
and reaches it.

**Effect.** Replaying genuine copies with rewritten stamps into a node's (predictable)
mark window can poison its phase statistics, block promotion, or — with the re-centre
— walk its anchor. The fallback is Mode A, the safe direction, but Mode B can be denied
at will.

**Fix direction.** Short term, on the node: feed phase and anchor only from the frame
being accepted now — a msgid above the replay counter, or a copy of the msgid just
accepted within its burst span — never from an older msgid. Longer term: authenticate
the timing claim itself, either by including the per-copy fields in the AAD (one GCM
operation per copy) or by a short per-copy CMAC under the session key.

### 3. A window end can close a window whose frame is being read — Medium (latent)

**Where.** `LoraInterface::windowEndClosesWindow` (`LoraInterface.cpp:315–349`) relies
on "the DIO0 task clears ValidHeader/RxDone only after `noteRadioSlept`". That is not
true: `serviceDio0Event` calls `lora_parsePacket(flags, 0)` (`frtosTasks.cpp:341`),
whose first act is `lora_clearInterrupts(irqFlags)` (`lora.cpp:583`). The FIFO read,
`lora_sleep` and `noteRadioSlept` come afterwards, in `onReceiveNew`.

**Why it can happen.** The DIO0 task (priority 8) and DIO1 task (priority 7) share
core 1 (`main.cpp:407–423`), and `spi_device_transmit` blocks the caller for every
single-register transfer of the FIFO read. A window end pending in that gap sees clear
flags, a modem no longer receiving and an unchanged generation, and closes the window:
it books a missed mark for a received frame, sleeps the radio (the SX1276 clears its
FIFO in sleep) while the DIO0 task is still reading, and gives the radio semaphore a
second time. The extended timer ends 58.9 ms into a window and a 58-byte frame's RxDone
lands ~57 ms in, so the timing is realistic. fw 1.0.91 showed 0 false closes in ~390
windows, so the gap is narrow, but the guarantee does not exist.

**Fix direction.** Move the window generation on (and stop the window-end timer) at the
start of `serviceDio0Event`, before `lora_parsePacket`; additionally refuse to close
unless the op mode is still RxContinuous. Test with the recorder: flags cleared, radio
in standby, then a window end — nothing closes.

### 4. A window extends without limit — Medium

**Where.** `LoraInterface.cpp:339–346`: any window end with RegModemStat bit 0 ("signal
detected") set re-arms the timer for another 29.44 ms. Nothing caps it; only the 1 s
stuck-window recovery (`kStuckWindowUs`, entered after a 700 ms semaphore wait) ends it.

**Effect.** Persistent in-band interference can keep a window open for over a second,
burning receive current and skipping the Mode A windows in between.

**Fix direction.** Cap extensions at what the longest downlink can need (its airtime
over the window width, ~4), and extend on bit 0 alone at most once; count cap hits.

### 5. A non-addressed frame leaves the mark open — Medium

**Where.** `noteMarkArmed` sets `mark_window_open_`; only `noteMarkHit` (addressed
frame) and `noteMarkMissed` (empty close) clear it (`CmdDispatcher.h:325–350`). The
DIO0 path clears nothing.

**Effect.** A mark window that receives a CRC-failed or a neighbour's frame leaves the
flag set. The next window that closes empty — a Mode A, beacon or Class A window that
was never a mark — calls `noteMarkMissed` and counts toward demotion. Separately, the
comment says a miss is "no frame addressed to me", but only empty windows count, so a
node that keeps hearing a neighbour instead of its own frame never demotes on missed
marks.

**Fix direction.** Decide the mark's outcome when its window closes, whichever path
closes it, and align the code with the stated rule.

### 6. Unlocked window generation — Low

`window_gen_` is a read-modify-write `volatile uint8_t` (`LoraInterface.cpp:263`,
`:597`) written from core 0 (arming) and core 1 (DIO tasks). A lost bump lets a stale
window end match a newer window. Use `std::atomic<uint8_t>` or a spinlock.

### 7. Reservation eviction — Low

`LORATracker::reserve_` (`lora_tracker.cpp:888–897`) overwrites the entry with the
earliest end when all eight are used, even if that entry is still in the future. Fine
while few spans are outstanding (marks are placed one at a time); unproven for bursts
queued in quick succession. Evict only expired entries and log when full.

### 8. NULL string in the config save — Low

`ConfigStore.cpp:341–342`: `strlen(cJSON_PrintUnformatted(root))` before the NULL
check at `:362`, with the temp file already open. An allocation failure crashes the
save. The atomic rename itself is sound.

### 9. Re-centre inside a residual fit — Low

The ModeTest residual fit (`CmdDispatcher.cpp:2520`) predicts from the live anchor.
A node that re-centres during a test (not promoted) folds the correction into
`residualPpm`; the Mode B residual test was adjusted for this. Count re-centres in the
ModeTest report so a residual taken across one is recognisable.

### 10. The published `symTimeout` is never applied — Low

**Where.** `handleGridSync` stores it (`CmdDispatcher.cpp:4060` → `gridstate::Params::sym_timeout`)
and nothing reads it back: `armTimedRxWindow` programs `timedgrid::kSymbolTimeoutSymbols`
(`LoraInterface.cpp:605`), and the RxContinuous window's width is `timedgrid::kWindowUs`
on the node's own timer. Same shape as §11a's "carried, validated, never read" items.

**Why it matters.** It is the hub's only runtime knob for the window width, so a deployed
node's window cannot be changed without a firmware flash — which is also what finding 11
would need.

### 11. A node past its coast limit demotes instead of widening — design option

Raised 2026-09-16 (question from the user: is the window widened when a beacon is missed?).
It is not. The window is fixed at 115 symbols / 29.44 ms with a ±14 080 us guard, and the
margin for a lost beacon is in the interval instead: the coast limit is `guard / ppm` —
704 s at the 20 ppm spec — and the hub publishes half of it (352 s) against a 349.5 s
beacon interval, so two intervals still fit. At node 2's measured ~9 ppm the limit is
~1 400 s, about four missed beacons. Past that the node demotes (SyncStale, or three
missed marks) to Mode A.

**The option:** widen the window by the predicted drift (elapsed × ppm, capped) rather
than demote. One ~40 ms window per round is far cheaper than Mode A's three per round, so
this is a power argument, not a reliability one. **Constraints:** the window must stay
under the 46.875 ms slot pitch (§4.4's "no second window fits" arithmetic), and
`ModeTestPolicy::periodsPhaseLock` takes the width as a parameter — it would have to be
given the real one rather than the assumed 29 440 us. Needs finding 10 fixed first if the
width is ever to be set from the hub.

### 12. HW-8's two observables are not reported — Low (measurement, not runtime)

Raised 2026-09-19, while trying to close HW-8 from the 1.0.95 Mode B report.

**Where.** Three gaps, none of which affects the running node:
* `noteModeTestOneShotError()` is called only under `grid_arm_fire_us_ != 0`
  (`LoraInterface.cpp:699`). A window whose one-shot never fired therefore records no
  sample, no log and no counter — exactly the event HW-8 exists to count is the one that
  leaves no trace.
* `LoraInterface::staleWindowEnds()` (`include/LoraInterface.h:297`, incremented at
  `LoraInterface.cpp:345`) has no caller outside `frtos_tasks_test.cpp`. It is never
  logged and never put in the report, so on hardware a stale window end is invisible.
  Same shape as finding 10's dead `symTimeout`.
* `ModeTestReport.oneShotErrorUs` is a `Hist` carrying min/p50/p95/p99/max/n, but the
  hub's REPORT line prints only `p99` and `n` (`lora_client.cpp:1626,1655`).

**Why it matters.** HW-8 is the early gate the whole timed design rests on, and its stated
criterion — "the histogram is bounded *and the miss count is zero*" — cannot be read off
the report, **not even by the method the code prescribes**. `lora_client.cpp:1660` states
it: *"HW-8's miss count is windowsArmed - n"*. That subtraction is invalid, because the two
counters span different populations:

* `windows_armed` increments only via `funnel_.noteWindowArmed()`, whose single caller is
  `noteMarkArmed()` (`CmdDispatcher.h:349`), reached from `LoraInterface.cpp:648` **only
  when `arm_source_ == ArmSource::Grid`**.
* `oneShotErrorUs.n` counts every **non-Trial** arm with a target — `Grid` **and
  `Beacon`** (`LoraInterface.cpp:684-701`).

So a beacon window contributes to `n` but never to `windowsArmed`, and the prescribed
difference goes NEGATIVE on a healthy run: the 1.0.95 report gives 590 − 593 = **−3**. The
−3 is not three phantom one-shots, it is the beacon cadence — `beacon slot 31 every 233
rounds` at 1.5 s per round is 349.5 s, so a 900 s test contains ~2.6 beacon windows.

The consequence is that **a real miss is currently unobservable in both directions**: it
leaves no counter of its own, and the subtraction meant to expose it is masked by an
unrelated population whose size depends on test duration. A run that genuinely lost three
one-shots would report `590 − 590 = 0` and read as perfect.

**Fix (revised).** Either count the misses directly at the arm site — an armed non-Trial
window that opens with `grid_arm_fire_us_ == 0` — or report `oneShotErrorUs.n` split by
`ArmSource` so the subtraction has a like-for-like denominator. Correct the comment at
`lora_client.cpp:1660` either way; as written it tells the next reader to compute a number
that cannot mean what it says.

**Fix.** Count the misses where they happen (an armed non-trial window that opens with
`grid_arm_fire_us_ == 0` is a miss), report that counter and `staleWindowEnds()` in
`ModeTestReport`, and print min/p50/max alongside p99. Small and host-testable.

### 13. A mark is booked as HIT with no check that the frame arrived in its window — Medium (measurement integrity) — **FIXED 2026-09-20, node 1.0.98 (`066e343`)**

**What shipped.** Four changes, each mutation-verified (M1–M4 all killed, host suite
1099/1099):
1. the hit is window-scoped — the generation is captured in `noteFrameArriving()`,
   carried in `rx_buffer_t::window_gen` as `rx_us` already is, mirrored to
   `last_rx_window_gen_` at the unpack site and compared in `admitFrame`. It cannot be
   read at dispatch time: `noteFrameArriving` bumps it before `lora_parsePacket` and
   `noteRadioSlept` bumps it again, so it is at least two windows stale by then;
2. `mark_hit_pending` is set on **unicast only**, so broadcast GridBeacon/GridDemote no
   longer close whatever mark is open;
3. a frame carrying no generation (`kNoWindowGen`) resolves nothing — fails closed;
4. extensions are suppressed while a sweep offset is active, so a deliberately
   mis-armed window is never carried back over the frame.

**Deliberately NOT changed:** the modem-status evidence in the extension condition. An
attempt to remove it (per the node review) broke three tests immediately, and they were
right — `AFrameArrivingAtTheWindowsEndKeepsItOpen` pins a frame synchronised on its
preamble at the window boundary, before ValidHeader lands. The 206 ms worst case is
finding 4's cap working as designed. Also unchanged: `missed_marks_` and
`last_addressed_us_` still reset on any unicast frame, because they answer "is the hub
serving this node at all", which does not depend on aim.

**Still to confirm on hardware:** whether the sweep is now offset-sensitive. The
measured `armed 189, hit 189` at +4 000, +16 000, +19 000 and −20 000 us was taken on
1.0.97 and should change. Until a point at +19 000 us reads `receives=no` with a high
armed count, HW-2 remains unmeasured.

Raised 2026-09-20, while HW-2's sweep reported 100 % reception at every offset tried.

**Where.** `CmdDispatcher.cpp:4660-4661` sets `mark_hit_pending = true` on a single
condition — `mine`, i.e. `destaddress` matches this node or is the broadcast address.
Nothing tests that the frame arrived inside the window the mark armed. `noteMarkHit()`
(4814) then resolves the open mark. The window generation exists and is used elsewhere
(`noteMarkMissed(generation)`, review finding 5), but the HIT path does not consult it.

**Why it matters.** Two observables lose their meaning:
* **WMR's hit half** counts "an addressed frame arrived while a mark was open", not "the
  mark's own window caught it". A node whose windows are mis-aimed but which still hears
  the hub by some other path reports a perfect window hit rate.
* **HW-2's sweep cannot measure `T_detect` through it.** The sweep's whole method is to
  arm the window deliberately early or late and ask whether the frame is caught. Measured
  on fw 1.0.97: `armed 189, hit 189` at **+4 000**, **+16 000**, **+19 000** AND
  **−20 000 us** — identical at both extremes of the control's full range. +19 000 opens
  the window at `T0 + 760 us`, after the preamble has ended; −20 000 opens it 38 ms early.
  Neither can catch the frame, and both reported 100 %. The offset is genuinely applied
  (hub writes `mt.armoffsetus`, node arms at `t0 - kArmLeadUs + arm_offset_us`,
  `armResidual p99` 412–464 us), so the arm really is displaced and the frames are caught
  regardless. **This is measured, not inferred: the observable is insensitive to the
  offset.**

**Mechanism — CORRECTED 2026-09-20 by the node review. The first explanation here was
wrong.** It claimed `armTimedRxWindow` re-arms continuous RX only `if (!cont_rx_armed_)`
so a late arm is a no-op. Those lines (`LoraInterface.cpp:569-577`) are
`armContinuousRx()`, the DRIFT-TEST path, whose own comment says it is armed once on
purpose. `armTimedRxWindow()` (`:582-627`) does the opposite: `noteRadioSlept()` →
`lora_idle()` → `lora_rxContinuous()` **unconditionally, every window**.

**The real mechanism is the window-end EXTENSION.** `windowEndClosesWindow` re-arms a
FULL `kWindowUs` whenever `(modem_st & kModemFrameArrivingMask) != 0` —
RegModemStat's signal-detected bits, which noise raises — up to
`kMaxWindowEndExtensions = 6` (`LoraInterface.cpp:352-361`). So a window can occupy
7 × 29.44 = **206 ms**. At arm offset −20 000 us the window opens at T0−38.2 ms and
would close at T0−8.8 ms; ONE extension carries it to T0+20.6 ms, spanning preamble,
sync and header. The frame is genuinely caught by a window that was supposed to miss —
at both extremes, with no other path needed.

**Second, independent cause (node review C2):** GridBeacon and GridDemote are addressed
to the BROADCAST address (`lora_tracker.cpp:728`), and the `mine` test at
`CmdDispatcher.cpp:4649-4651` accepts broadcast — so **every beacon sets
`mark_hit_pending`** and closes whatever grid mark is open. The phase path explicitly
refuses `CMD_GRIDBEACON` (`:4860`); the hit path does not. This inflates `windows_hit`
by ~1 per 233 rounds and is part of the `armed 590 / hit 589 / oneShot 593` arithmetic
finding 12 could not reconcile.

**Fix — ALSO CORRECTED.** "Record the generation at `noteMarkArmed()` and compare"
cannot work: by the time the dispatcher resolves the hit (`:4814`), `window_gen_` has
been bumped twice — `noteFrameArriving()` at `LoraInterface.cpp:309` (deliberately
before `lora_parsePacket`) and `noteRadioSlept()` at `:263`. The generation must be
**captured at RxDone and carried with the frame** in `rx_buffer_t`
(`CmdDispatcher.h:50-59`), exactly as `rx_us` already is, then checked at dispatch.
Excluding broadcast frames fixes the beacon half in one line, or falls out of the
generation check.

For HW-2 specifically, extensions must also be forced to 0 while `sweepMisArming_()` is
true, or a deliberately mis-armed window still extends onto the frame. Until all of this
lands, treat `windows hit` as "the node was served, or heard a beacon, while a mark was
open" — **not** as a Mode B pass criterion. The ARMED half is sound; it comes from
`ArmSource::Grid` at the radio (`LoraInterface.cpp:648`).

## Checked and found sound

* SPI register access is serialised by a mutex per transaction (`lora.cpp:118–240`).
* `TICKS_TO_WAIT` is 1; no interrupt event is decimated with its pin left disabled.
* The node's unprovisioned-bootstrap exemption passes only ClientConfig and CoverConfig,
  only while its address is 0 (`CmdDispatcher.cpp:4801–4810`).
* The config save writes beside and renames over; LittleFS replaces the target.
* Protocol numbering: the new response field 23 (`GridSyncRequest`) and the operation
  field 23 (`GridBeacon`) live in different messages; a node or hub that does not know a
  new field ignores it.

## Known and accepted, not re-reported

* Plaintext `CMD_LOGIN` is the node's one deliberate exemption (plan, section 11b); a
  forged LoginMsg can still cost a session.
* A node without a fleet key accepts unsigned beacons (bounded re-anchor), and
  GridDemote is unauthenticated by design (safe direction).

## Scope and limits

Reviewed in depth: the node receive and window path (LoraInterface window code,
`serviceDio0Event`/`serviceDio1Event`, task placement), the trust placed in header
timing, hub uplink acceptance and dispatch, GridSync publish/re-publish/request, the
config save and the hub reservation table.

Not reviewed line by line: ModeTest internals, Mode C wake clock, auto mode and the
scheduler, AckCache and TxQueue, `lora_tracker` placement arithmetic beyond
reservations, `loracover`, and the YAML.

## Suggested order

1 and 3 first — both small and testable on the host. Then the short-term half of 2,
then 4 and 5, then the rest. None of them affects the running bench measurement; fw
1.0.93 should not go to a field node before 1 and 3.
