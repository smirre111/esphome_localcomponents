# Runbook: build, test, flash, OTA, regression, traps

Practical procedures for the LoRa blinds hub and node, distilled from four production rollouts (2026-10-19 .. 2026-11-03). Companion to `docs/project-state.md` (what is true now) and `docs/bench-runbook.md` (bench measurement theory). Shell notes: the Bash tool is Git Bash (C: = `/c/...`); WSL has cmake/ctest/g++/protoc-c/lizard; PowerShell is the right place for git (never run `git status` from WSL on these repos). Anything with `$`, quotes or control flow that goes through PowerShell into `wsl` belongs in a script file run as `wsl -e bash /mnt/c/.../script.sh`.

## 1. Build and test

**Node host tests** (WSL): `cmake -S test -B ~/nodehost && cmake --build ~/nodehost -j8 && (cd ~/nodehost && ctest -j4)`; fork-per-case runners accept a case name as argv[1] (use it for mutation checks). 27 ctest entries at 747c88a; two of them (`stubs_node_vs_hub_{c,h}`) are red by design whenever the hub copy of the stubs lags the node.
**Node firmware**: IDF 6.0 only (`C:\Development\esp\v6_0\v6.0\esp-idf`, `. export.ps1`), `idf.py -C C:\Development\PlatformIO\PlatformIO\BlindsESP build` -> `build/BlindsV3.bin`. `PROJECT_VER` fields are 0-99 each (a field above 99 makes the node report fw 0 and the hub never single-shots it). Bump `PROJECT_VER` for every build that is flashed: the beacon `fw=NNNNN` (1.1.57 -> `10157`) is the only proof of what runs.
**Hub host tests** (`tests/proto_sim`, WSL): `cmake -S tests/proto_sim -B ~/psbuild && cmake --build ~/psbuild -j8 && (cd ~/psbuild && ctest -j4)`. proto_sim compiles REAL node sources: it takes them from the node repo's `test/node_dispatcher_sources.cmake` and the node tree (tests include `CmdDispatcherTestPeer.h`, so the hub needs a node tree that has it, i.e. node >= 747c88a / the review-n19 merge). When the node repo is being changed by another agent, measure against a clean snapshot: `git archive <node sha> | tar -x -C <scratch>`. Always check the build's own exit status; ctest reports PASS on a stale binary. `PROTO_SIM_GOLDEN_RECORD=1` only chained with `&&` after a successful build, then inspect the golden diff. Drift gates must read PASSED; a gate that cannot run now shows as SKIPPED (with `CI` set a missing node tree fails configure). `python tools/layer_lint.py` must show no metric above `tools/layer_lint_baseline.json` (a ratchet: lower the baseline when a count goes down, never raise it).
**Complexity**: `lizard -l cpp local_components -x "*blinds.pb-c.*"` in WSL; at 2026-11-03 nine functions exceed CCN 10, max 17.
**Hub firmware compile**: `esphome compile loradevices.yml` (Windows, ESPHome 2026.2.1) ~170 s. Run `esphome clean` first when a .cpp was added (CMake glob). Build from a SHORT path: the scratchpad path is too long for PlatformIO (WinError 206), so snapshot with `git archive <sha> | tar -x -C C:\hsrN` (+ copy the untracked `secrets.yaml`) and compile there. `rm -rf` of `C:\` dirs is blocked by the safety check: use a fresh directory name per snapshot and ask the user to delete old ones. The generated `config_hash` depends on the build path; do not compare hashes across snapshot dirs.
**Stubs**: `proto/regen_stubs.sh` (node repo, WSL; LF endings enforced by `.gitattributes`) rewrites the node copy and the hub vendored copy; the hub list of vendored files is `tests/proto_sim/cmake/vendored_shared_headers.txt`. Reordering fields inside a protobuf message changes the C struct layout even with unchanged numbers.
**Editing**: files are CRLF or LF per file; use Python `rb`/`wb` or the Edit tool, never `sed -i` or PowerShell `Set-Content -Encoding utf8` (BOM). Mutation checks: whole-line anchors, assert the anchor count is 1, rebuild before the verdict, `touch` after a manual revert, never pipe the run through something that can truncate before the file is restored.

## 2. Flashing order and recipes (production)

Order, always: **node 1 OTA -> node 2 serial -> hub last.** No backward compatibility is needed, but a new node image must boot against the OLD hub, and the hub flash follows. Only do this when the user has said so in chat (the permission classifier blocks production deploys otherwise).
1. Verify HEADs and clean trees (PowerShell git). Back up `BlindsESP\https_hosted\BlindsV3.bin` (the OTA server serves THIS file, not the build dir; WSL `openssl s_server -WWW` on port 8070, node reaches `https://schmidteinander.local:8070/BlindsV3.bin`) into the scratchpad `images/`, copy the new `build/BlindsV3.bin` over it, check the served sha: `curl -sk https://localhost:8070/BlindsV3.bin | sha256sum`.
2. Start the OTA download capture BEFORE pressing the button (the server writes no access log): `tools/campaigns/ota_ss.sh` (polls `ss -tni '( sport = :8070 )'` once a second; start it via PowerShell `Start-Process wsl.exe`). Node 1 is 192.168.178.51.
3. Node 1: `python tools/hubctl.py press "Trigger OTA1"` (or `curl -X POST -d "" "http://192.168.178.91/button/Trigger%20OTA1/press"`). The node must be awake with a live session. The OTA sysop is acked, the node downloads (~10-20 s), reboots; expect the beacon `fw=` of the new version within ~25-30 s. After an OTA reset node 1 believes its position is 0.00 (send "open" once to realign). If it does not return: do NOT power-cycle blindly: check whether the hub still receives its 15-min battery uplinks (it may be DEAF rather than silent: see section 5) and flash the new hub (its FCNT-jump detection recovers a deaf node).
4. Node 2 (COM6, FTDI; hub is COM9, CP210x; never infer the mapping from the chip): free the port, then `python -m esptool --chip esp32 -p COM6 write-flash 0x1000 build\bootloader\bootloader.bin 0x20000 build\BlindsV3.bin` (add `--flash_mode`/`--flash_freq`/`--flash_size` as in `build\flash_args` if esptool complains) (bootloader + app only; NEVER erase NVS/storage 0x633000 = LittleFS provisioning; `idf.py flash` would wipe storage, `app-flash` writes only the app). If the node ever did an HTTPS-OTA, also `erase-region 0x630000 0x2000` (otadata) or the bootloader keeps booting the OLD OTA slot; confirm with the boot banner `Loaded app from partition at offset 0x20000` + `App version: X`. Closing/opening the serial port can reset the node (an EN reset is a POWERON reset and clears RTC RAM).
5. Hub: `esphome run`/upload over OTA to 192.168.178.91 (benchlog holding COM9 reboots the hub every time it opens the port, so OTA is the usual route). Production = `loradevices.yml`; bench = `loradevices.bench.yml` from `tools/make_bench_yaml.py` (git-ignored; adds Mode Test/MAC Ping buttons, node 2 check-in 5 min, replaces the 23:00 sleep actions by log lines; for a sleep test generate a variant with `sleep_duration: 600`). Always restore PRODUCTION afterwards. `preferences: flash_write_interval: 30min` loses switch changes made within 30 min before a reflash (press `Hub Restart` to flush).
6. Verify: both nodes `Login acknowledged`, `Onboarding done`, encrypted GridSync acked, Mode B `RE-ESTABLISHED` by itself within ~3-10 min (Timed Mode switches are restored by `RESTORE_DEFAULT_OFF` = last state), cover ops 0.9 then open acked once each, no `ACK_ERROR`. WAIT ~85 s between cover ops (the node is deaf while the motor runs; a second op sent too early gets four retries and a forced relogin). The second op ~25 s after a move always misses its optimistic single shot and is acked after the burst fallback: known, benign.
7. Keep an `esphome logs <yaml> --device <ip>` API connection open during any bench session (the hub reboots every ~15 min without a native-API client and loses session state); on Windows set `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8`. `tools/benchlog.py` needs two REAL serial ports.

## 3. Regression campaign (node 2 only)

`tools/make_bench_yaml.py` -> flash the bench yaml -> run a campaign driver (`tools/campaigns/review_campaign3.py <session_dir>`, or `tools/mac1_turnaround.py` / `tools/mac2_campaign.py`) from the hub dir with `tools/benchlog.py` capturing both serial ports (+ `esphome logs`). Steps: Mode A MAC-1 turnaround, Mode A MAC-1+MAC-2, then Timed Mode ON, wait `RE-ESTABLISHED`, 60 s quiet, 900 s Mode B + crypto. Node 1 Timed Mode OFF during the campaign (restore afterwards, then `Hub Restart`), node 2 Timed Mode OFF for the Mode A steps. Drivers must end a step only on `[RollladenWohnzimmer2] ModeTest REPORT` (node 1's warm-up REPORT otherwise ends it early); the hub can miss a REPORT while it transmits marks: the node's own serial `ModeTest REPORT` line has the numbers. Compare with `docs/project-state.md` section 6. Stack headroom is read from the hub's periodic log lines (production send task ~1350 of 4096, esp_timer ~1700+).

## 4. Useful live checks

Hub web server: SSE `curl -s -N http://192.168.178.91/events` (`event: state` frames carry entity states), entity-NAME URLs `/switch/Optimistic%20single%20shot%20(node%202)` (a wrong object-id URL returns an EMPTY body, not an error; print byte counts), `tools/hubctl.py` (HTTP Basic auth). `Sleep now (node N)` diagnostics exist for sleep tests. Log lines worth grepping: `Beacon: reason=`, `Login acknowledged`, `Onboarding done`, `Node restored its counters (uplink FCNT +N`, `SLEEP command UNCONFIRMED`, `Config acknowledged by the node`, `Config unchanged since last boot`, `REGISTER replayed`, `REGISTER rate-limited`, `Mode B RE-ESTABLISHED`, `No free buffers`, `ANCHOR SUSPECT`. Time is HH:MM:SS only: do not compare log times as strings across days. A silent serial port means a sleeping node, not a dead one: `python -m esptool --chip esp32 -p COM6 --after hard-reset chip-id` resets it deliberately.

## 5. Traps that cost time (each happened at least once)

- **Reading logs wrongly**: an hours-long absence of node 1 in the hub's Login/Beacon lines on 2026-10-31 looked like "off the air"; hub.log showed its 15-min battery uplinks were accepted the whole time. The node was DEAF (see `docs/reviews/review-ota-hang-2026-11-01.md`): lost boot beacons, hub downlink FCNT inside the node's restored replay floor. Fixed (node 1.1.56 boot fallback, hub FCNT-jump detection). Always look at what the hub actually received before saying a node is gone.
- **Soft-reset path**: an RTS/DTR serial reset is a POWERON reset (REGISTER path, RTC cleared), it does NOT exercise the F-5 resume path. To exercise F-5 use `Trigger OTA2` with a same-version image (node aborts on same version and ends in a real SW reset with RTC valid); the hub then retries the unacked OTA sysop and forces a relogin (benign).
- **Nightly sleep at 23:00** runs inside any bench session that keeps the production schedule: the bench yaml replaces it, verify the generator assertion held. Two nodes slept in the same minute collided on the air before the SLEEP gate existed.
- **Hub sleep record stale after restart with a different sleep_duration** was fixed (record stores the commanded duration); a lost ClientConfig used to leave node 2 on `sleepDuration 600`: check `sleep=21600 batt=900` after any bench variant (node 2: serial config dump; node 1 has no serial: hub logs `Config acknowledged ... in sync`).
- **Rate-limit pauses** of hours leave the bench yaml on the hub: re-check `date` and the process list after any interruption and restore production.
- **Snapshots**: `C:\hs*` dirs are only deletable by the user; use new names.
- **PowerShell `$?` prints `True`** and a failed build then reads as a pass; use script files.
- **Mode B phase error** and H-1 numbers vary a lot between runs: judge by FER_link, MIC_FAIL, gaps and the per-length table, not by one p50.
